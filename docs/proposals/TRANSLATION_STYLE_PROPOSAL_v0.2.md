# แนวทางการแปลภาษาไทย — Two Point Campus Thai Mod (v0.2)

ผู้เสนอ: Claude (Translator) · ผู้ตรวจ: Controller · วันที่: 2026-10-15
สถานะ: **ฉบับปรับตามผลตรวจใน `docs/TRANSLATION_STYLE_REVIEW.md` เสนอให้ Controller ตรวจซ้ำ** เป็นกรอบบรรณาธิการชั่วคราว กฎที่ขึ้นกับ runtime (การตัดบรรทัด ฟอนต์ ตัวอักษรพิเศษ รูปแบบ token) และศัพท์ทั้งหมดยังเป็น provisional
ลำดับความสำคัญ: ถ้าเอกสารนี้ขัดกับผลตรวจของ Controller ให้ยึดผลตรวจ v0.1 (`TRANSLATION_STYLE_PROPOSAL.md`) เก็บไว้ตามเดิม ไม่ถูกแก้
Glossary: ดู `GLOSSARY_v0.2.md` (คอลัมน์บริบทและสถานะอนุมัติ)

ยังไม่มีการแปลจำนวนมาก และไม่มีการสร้างข้อความต้นฉบับ ทุกตัวอย่างรูปแบบ token ด้านล่างเป็นภาพประกอบทั่วไป **ไม่ใช่ข้อเท็จจริงของ Campus** จนกว่า Controller ยืนยัน schema

## 1. สิ่งที่ Controller รับไว้แล้ว (คงเดิมจาก v0.1)

ภาษาไทยธรรมชาติและกระชับ คำสั่งในเกมชัดเจน ข้อความระบบเป็นกลางไม่ระบุเพศ ไม่ใช้คำลงท้ายในข้อความระบบ ใช้น้ำเสียงเฉพาะตัวละครได้เมื่อบริบทรองรับ รักษามุกที่ตั้งใจและบันทึกการดัดแปลง คง stable ID และตัวตน จำนวน และรูปแบบของ token ทุกตัว ไม่ "แก้" token ต้นฉบับที่น่าสงสัยโดยเงียบ แยกต้นฉบับกับคำแปลออกจากกัน และธงความกำกวม

## 2. น้ำเสียงและระดับภาษา

- ภาษากึ่งทางการแบบสมัยใหม่ ไม่ใช้ราชาศัพท์หรือภาษาราชการ เว้นแต่ต้นฉบับตั้งใจล้อ
- ผู้เล่น = "คุณ" เป็นค่าเริ่มต้น เลี่ยง "ท่าน" และการระบุเพศ
- ไม่ใช้ ครับ/ค่ะ/นะ/จ้ะ ในข้อความระบบ ใช้ได้เฉพาะเสียงตัวละครที่บริบทยืนยัน พร้อมหมายเหตุ
- ตามชนิดข้อความ: ป้ายและปุ่ม = วลีสั้นไม่มีจุด · Tooltip = ประโยคสั้นภาษาพูดเบา ๆ · Tutorial = ชัดเจนทำตามได้โดยไม่ต้องเดา · แจ้งเตือนที่กระทบเกมเพลย์ = ชัดก่อนตลก · ข้อความตลก/ประกาศ = อิสระได้มากสุด
- ประเภทข้อความข้างต้นเป็นแนวทางเริ่มต้น ผู้แปลจะยืนยันจากบริบทที่ Controller ให้ ไม่เดาจากรูปประโยค

## 3. ความยาวและความกระชับ (แก้ตามข้อ 1 ของผลตรวจ)

- **ยกเลิกเกณฑ์อัตราส่วน 1.3 เท่าของจำนวนอักขระ** จำนวนอักขระใช้ตัดสินว่าพอดี UI ไม่ได้ เพราะอักขระผสมของไทยและเมตริกฟอนต์ ไม่สมมติว่าไทยกว้างกว่าอังกฤษโดยทั่วไป
- ผู้แปลเขียนให้กระชับตามธรรมชาติภาษา (เลือกคำสั้นที่คนใช้จริง ตัดคำเชื่อมที่ไม่จำเป็น) แต่ไม่ถือเป็นการรับประกันว่าพอดี
- ธงเพื่อคัดกรองเท่านั้น: `LENGTH` (สงสัยว่าอาจล้นพื้นที่) และ `WRAP_CONCERN` (สงสัยปัญหาการตัดบรรทัด) ใช้จนกว่า QA วัดการแสดงผลจริง
- บันทึกข้อจำกัดความกว้าง/จำนวนบรรทัดของ UI เมื่อ Controller ให้ข้อมูล (ดูข้อ 9 เรื่อง `max_len_hint`)
- ไม่แก้ปัญหาความยาวด้วยการเว้นวรรคแปลก ๆ การตัดคำกลางคำ หรือการแทรกอักขระที่มองไม่เห็น
- ตัวเลข หน่วย และสัญลักษณ์: คงตามต้นฉบับ ไม่ใช้เลขไทย เว้นแต่ Controller สั่งเป็นกรณี คำย่อใช้เฉพาะที่ Glossary อนุมัติ

## 4. การรักษามุก

เป้าหมาย: คนไทยขำที่จุดเดียวกับที่ต้นฉบับตั้งใจ ไม่ใช่แปลตรงตัว

- ระดับการแปลมุกเป็น **ฟิลด์เสริม ใช้เมื่อข้อความมีมุกเท่านั้น** (`joke_tier` ว่างได้สำหรับข้อความทั่วไป): T1 แปลตรงแล้วยังตลก · T2 ดัดแปลงอ้างอิง/ตัวอย่างให้คนไทยเข้าใจ · T3 เขียนมุกไทยใหม่ทำหน้าที่เดียวกัน (ตำแหน่ง น้ำเสียง ขนาด)
- ห้ามอธิบายมุกในตัวข้อความ ห้ามเพิ่มมุกในข้อความที่ต้นฉบับไม่ตลก ห้ามตัดมุกทิ้งเพราะแปลยาก ถ้าแปลไม่ได้ให้ธง `JOKE_UNRESOLVED` พร้อมตัวเลือก 2–3 แบบ
- T2/T3 ต้องมี `translator_note` (ต้นฉบับเล่นอะไร ทำไมเลือกแบบนี้)
- ห้ามเพิ่มการอ้างอิงบุคคลจริง แบรนด์จริง หรือเหตุการณ์จริง ผู้แปลเสนอได้ แต่ต้องให้ Controller อนุมัติ
- **ไม่นำข้อความ Museum มาใช้เป็นข้อความ Campus** ตามผลตรวจ: Museum เป็นแหล่งอ้างอิงงานวิจัยด้านการแสดงผลเท่านั้น ยังไม่มีคลังข้อความ Museum ที่อนุมัติให้ใช้ซ้ำด้านศัพท์ ผู้แปลจะไม่ใช้ข้อความ Museum จนกว่า Controller ส่งชุดแยกและอนุมัติเป็นกรณี

## 5. Tokens และ markup (แก้ตามข้อ 3 ของผลตรวจ)

**หลักการ: แยก "ข้อความที่ถอดรหัสแล้ว" ออกจาก "ไบต์ที่ serialize"** ผู้แปลทำงานกับข้อความที่ถอดรหัสแล้วตามที่ Controller ส่ง การเข้ารหัส/escape กลับเป็นหน้าที่ของเครื่องมือ export/import ไม่ใช่ของผู้แปล ผู้แปลไม่พิมพ์ escape ด้วยมือเพื่อ "ให้ถูกรูป" เอง

### 5.1 สิ่งที่ผู้แปลต้องรักษา

- **ตัวตนของ token:** รูปแบบไวยากรณ์ของ token ต้องคงตามต้นฉบับทุกตัวอักษร ห้ามแปลชื่อภายใน ห้ามเว้นวรรคเพิ่มเข้าไปใน token
- **จำนวน token:** แต่ละชนิดมีจำนวนเท่าต้นฉบับ เว้นแต่ schema จริงระบุว่าอนุญาตให้ละหรือซ้ำ
- **ความหมายของ escape:** คงความหมายตามต้นฉบับ ไม่เปลี่ยน newline จริงเป็นตัวแทนหรือกลับกันด้วยตัวเอง
- **รูปแบบ format spec** (เช่นรูปแบบตัวเลข, printf) คงเดิม
- ตัวอย่างประเภท token ที่อาจพบ (ต้องยืนยัน): ชื่อ/ดัชนีในปีกกา, printf, rich-text tag, อ้างอิง key ภายใน, อักขระควบคุมในต้นฉบับ

### 5.2 การสลับลำดับ

- **printf แบบเรียงลำดับ** (`%s %s`, `%d %d`): ห้ามสลับ ต้องคงลำดับ ถ้าประโยคไทยต้องสลับ ให้ธง `REORDER_NEEDED`
- **token แบบมีดัชนีหรือชื่อ:** สลับได้ **เฉพาะหลังจาก Controller ยืนยันว่า parser จริงรองรับ** จนกว่าจะยืนยัน ให้คงลำดับ และธง `REORDER_NEEDED` เมื่อภาษาไทยต้องการสลับ

### 5.3 Markup

- ตรวจ markup ในเชิงความหมาย ไม่บังคับให้ทุก tag มีปิดครบคู่ เพราะมี tag แบบ self-closing หรือไม่ต้องปิดได้ (เช่น แทรกสไปรต์ ขึ้นบรรทัด)
- ห้ามเปลี่ยนค่าแอตทริบิวต์ ห้ามเพิ่มหรือลบ tag ถ้า tag ครอบข้อความที่หาคำเทียบเท่าไม่ได้ ให้ธงและห้ามย้าย tag ไปครอบคำอื่นโดยเงียบ ๆ
- ตัวตรวจอัตโนมัติจะเขียนหลังรู้ไวยากรณ์จริง จนกว่านั้นตรวจด้วยการเปรียบเทียบชุด token ต้นฉบับ/คำแปล ไม่ตรวจด้วยสายตา

### 5.4 บรรทัดใหม่

การเปลี่ยนจำนวนหรือตำแหน่งตัวแบ่งบรรทัด ต้องตรวจเทียบกับรูปแบบต้นฉบับจริงและบริบท ผู้แปลไม่เพิ่มหรือลดตัวแบ่งบรรทัดเอง ถ้าความยาวน่ากังวลให้ธง `WRAP_CONCERN` แทน

### 5.5 การเว้นวรรครอบ token — **ข้อเสนอ ยังไม่เป็นกฎ**

ข้อเสนอจาก v0.1 ถูกลดสถานะเป็นสมมติฐานรอทดสอบ: เว้น 1 ช่องระหว่างตัวเลข/token กับลักษณนามหรือหน่วยไทย และระหว่างข้อความไทยกับ token ที่อาจเป็นข้อความอิสระ ให้ QA ทดสอบรูปแบบนี้เทียบกับแบบติดกัน ก่อน Controller ตัดสินใจ

## 6. อักขระและ Unicode (แก้ตามข้อ 2 ของผลตรวจ)

- **ยกเลิกข้อจำกัด "เฉพาะ Thai + ASCII"** เครื่องหมายวรรคตอนเดิม อักษรอื่นในชื่อเฉพาะ และสัญลักษณ์ในต้นฉบับอาจจำเป็น
- **ธงอักขระใหม่:** อักขระใดที่ผู้แปลนำเข้ามาใหม่และไม่ปรากฏในต้นฉบับ ให้ธง `NEW_CHAR` เพื่อให้ตรวจ glyph coverage
- **ปฏิเสธ:** อักขระควบคุมที่ไม่ได้ตั้งใจ, U+FFFD (replacement character), อักขระที่มองไม่เห็นที่เพิ่มเข้ามา อักขระควบคุมที่มีอยู่ในต้นฉบับโดยตั้งใจให้คงตามรูปแบบที่ยืนยัน
- **ไม่มีกฎลำดับ พยัญชนะ → สระ → วรรณยุกต์ แบบสากล** อักขรวิธีไทยมีลำดับที่ขึ้นกับบริบท ผู้แปลพิมพ์ด้วยคีย์บอร์ดปกติ ธงลำดับที่น่าสงสัย (`SUSPECT_SEQ`) แต่ไม่ normalize หรือสลับลำดับโดยเงียบ
- **สระอำ:** ข้อความที่เขียนใหม่ใช้ U+0E33 ตัวเดียว เป็นความชอบด้านบรรณาธิการ ไม่ใช่ข้อเรียกร้องของ renderer ลำดับที่เกี่ยวข้องให้ QA ทดสอบ
- **ห้ามแทรกอักขระที่มองไม่เห็น** (ZWSP, ZWNJ, NBSP ฯลฯ) เป็นวิธีแก้ปัญหา จนกว่า prototype และ QA ยืนยัน
- ตัวเลขคงเลขอารบิก ไม่แปลงเป็นเลขไทย

## 7. พหูพจน์ เพศ และโครงสร้าง runtime (แก้ตามข้อ 4 ของผลตรวจ)

- **คงทุก key, branch, selector และ token ของต้นฉบับ** ไม่ยุบโครงสร้างและไม่ลบ key ใด
- ภาษาไทยไม่มีรูปพหูพจน์ ดังนั้นคำแปลของแต่ละ branch **ซ้ำกันได้เมื่อเหมาะสมทางความหมาย** แต่ผู้แปลตรวจบริบทก่อนว่า singular/plural มีความหมายต่างกันจริงหรือไม่ (เช่น เลขที่นำมาเปรียบเทียบ "1" กับ "หลาย") หากต่างจริง ห้ามลบความต่างนั้น
- ธง `PLURAL_REVIEW` เมื่อสองสาขาแปลเหมือนกัน เพื่อให้ Controller ตรวจกลไก key

## 8. ชื่อเฉพาะ (แก้ตามข้อ 6 ของผลตรวจ)

- **คงการสะกดตามต้นฉบับเป็นค่าชั่วคราว**
- พิจารณาแปล/ถอดเสียงเป็นรายกรณี โดยเฉพาะชื่อห้องและชื่อวิชาที่ผู้เล่นเห็นขณะเล่น **ไม่สมมติว่าชื่ออังกฤษช่วยประหยัดความกว้าง**
- บันทึกการตัดสินใจที่อนุมัติแล้วตาม entity/key ใน Glossary ไม่ตัดสินใจนโยบายรวม

## 9. ฟิลด์ของ record (แก้ตามข้อ 7 ของผลตรวจ)

**ยังไม่กำหนด schema บังคับ** รอ extraction ระบุ ID จริงและไวยากรณ์ token ฟิลด์ต่อไปนี้เป็นข้อเสนอที่ผู้แปลอยากใช้:

| ฟิลด์ | สถานะ | คำอธิบาย |
|---|---|---|
| `translator_note` | เสนอ | เหตุผลการเลือกคำ ที่มาของมุก |
| `flags` | เสนอ | ชุดธง (ดูด้านล่าง) |
| `alt` | เสนอ | ตัวเลือกอื่น |
| `joke_tier` | **ไม่บังคับ** | เฉพาะข้อความที่มีมุก |
| `max_len_hint` | **ไม่บังคับ / คำแนะนำ** | ถ้ามี ต้องระบุ **หน่วย** (เช่น px, จำนวนบรรทัด, หน่วยฟอนต์) ความกว้างที่เรนเดอร์จริงและข้อจำกัดบรรทัดดีกว่าเมื่อมีข้อมูล ห้ามใช้จำนวนอักขระเป็นค่ากำหนดการยอมรับ |

ธงที่ใช้ (ทั้งหมดเป็นการคัดกรอง ไม่ใช่ pass/fail): `LENGTH`, `WRAP_CONCERN`, `REORDER_NEEDED`, `PLURAL_REVIEW`, `AMBIGUOUS`, `JOKE_UNRESOLVED`, `TOKEN_ANOMALY` (token ต้นฉบับน่าสงสัย ไม่แก้เอง), `NEW_CHAR`, `SUSPECT_SEQ`

## 11. สถานะคำถามเดิมและคำถามใหม่

ตอบแล้วโดยผลตรวจ: schema/บริบท (ยังไม่มี) · การตัดบรรทัด/ฟอนต์/ZWSP/NBSP (รอ prototype และ QA) · Museum (อ้างอิงงานวิจัยการแสดงผลเท่านั้น) · ช่องทางส่ง (ไฟล์ที่ผู้ใช้ส่งต่อได้ ข้าม GitHub ไปก่อน)

**ยังเปิดอยู่:** (1) ผู้แปลยังไม่ได้รับชุดข้อความที่สกัดจากเกม (2) เมื่อได้ชุดข้อความ ขอบริบทต่อรายการ: ประเภท UI, ตำแหน่งที่ใช้, ตัวละคร/เสียง, ข้อจำกัดความกว้าง/บรรทัด พร้อมหน่วย (3) ไวยากรณ์ token จริง และ parser รองรับการสลับลำดับ token ที่มีดัชนี/ชื่อหรือไม่ (4) ความหมายของ key เอกพจน์/พหูพจน์ในต้นฉบับ (ถ้ามี) (5) นโยบายคำลงท้ายของตัวละครเฉพาะ เมื่อเห็นบริบท

## 12. แผนถัดไป (ยังไม่ดำเนินการ)

รอชุดข้อความที่ Controller สกัดและอนุมัติ จากนั้นผู้แปลจะเสนอแปลชุดนำร่อง 40–60 ข้อความ เพื่อหารือศัพท์ (ปิดรายการ NEEDS_CONTEXT ใน Glossary) ก่อนแปลจำนวนมาก ผู้แปลจะไม่คิดข้อความต้นฉบับเองและจะไม่เริ่มแปลก่อนได้รับงานมอบหมายที่ชัดเจน

## 13. รายการตรวจก่อนส่งทุกชุด

- เปรียบเทียบชุด token ต้นฉบับกับคำแปลด้วยสคริปต์ (ชนิด จำนวน ลำดับสำหรับ printf) ไม่ใช้สายตา
- markup ตรวจเชิงความหมาย ไม่ย้าย tag ข้ามความหมาย
- ตัวแบ่งบรรทัดไม่เปลี่ยนโดยไม่มีเหตุและบริบท
- ไม่มีอักขระควบคุมโดยไม่ตั้งใจ U+FFFD หรืออักขระที่มองไม่เห็นที่เพิ่มเข้ามา อักขระใหม่ถูกธง
- ศัพท์ตรงกับ Glossary ตามสถานะ (เฉพาะรายการที่อนุมัติ)
- ทุกข้อความที่ธงมี `translator_note`
